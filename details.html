Geometry-Aware Map Editing, explained from first principles

The stakeholder document is a list of letters: P, R, F, L, E, C. Each letter is the answer to one problem, and the problems come one after the other. This page walks that chain so every piece lands in a place, and ends with one request followed through all of it with real numbers.

What this page is, and is not It explains what the framework asks for and why. It is not the GREM-4 design and it is not a build plan. Where I give my own opinion rather than the document’s, it is marked [my reading]. Numbers in the examples were computed, but the example map is invented. Check geometry rules against the ASAM OpenDRIVE 1.9.0 spec before relying on them.

Colour code. model = what a language model is good at (meaning, choosing, referring). code = what deterministic code does (exact numbers, checks, decisions). That split is the whole document.

1. OpenDRIVE in five minutes (just what you need)

You know the XML. This is the geometric meaning behind the tags, in the five ideas the framework relies on.

  1. Reference line. Each road has one curve (the spine). It is built from pieces (<geometry>): line, arc, spiral, poly3, paramPoly3. Each piece stores a start s, start x, y, heading, and a length.
  2. s and t. A position on the road is (s, t): s = distance along the spine, t = sideways offset (left positive). Converting (s, t) to world x, y needs the geometry maths. Worked example: an arc with curvature k = 0.01 (radius 100 m), starting at (0, 0) heading 0. At s = 50 the heading is k·s = 0.5 rad = 28.65°, the spine point is x = sin(0.5)/0.01 = 47.943, y = (1 − cos 0.5)/0.01 = 12.242. A point 4 m to the right (t = −4) is displaced along the left normal (−sin h, cos h), giving x = 49.860, y = 8.731.
  3. Lanes. Lanes are numbered outward from the centre: right side −1, −2, …, left side 1, 2, …; lane 0 is the centre line (a marker, not a driving lane). A lane’s width is not stored as one number. It is a cubic: w(ds) = a + b·ds + c·ds² + d·ds³ starting at a given offset.
  4. Lane sections. A road is cut into lane sections (along s). Inside a section the lanes are fixed; at a new section the lane count can change. Lanes in neighbouring sections are connected by <link>.
  5. Objects, signals, junctions. Signals and objects are things placed at (s, t). Roads connect to other roads, directly (predecessor/successor) or via junctions.
Hold this thought Nearly every number in a file is a generating parameter, not a value you can read. You cannot see a lane’s width at s = 137 without evaluating a cubic that starts somewhere else. This is the root of premise P4.

2. The one idea behind the whole document

Everything in the document follows from one observation:

A language model is good at Meaning. “Signal 55” → which signal. “Before the junction” → which end of the road, which side. “Add some signs” → this is too vague, ask.
A language model is bad at Exact values. It will write 190.002 when the answer is 190.0, or a coefficient that is right to three decimals and wrong at the fourth. Plausible-wrong survives review far better than obviously-wrong, which is what makes it dangerous.

The document states it as a single hard rule:

The invariant No value that reaches the map originates in the model. Coordinates, coefficients, lengths and positions come from deterministic computation. The model selects, references and composes them.

The rest of the document asks: what must the system look like so that this works? The answer needs (a) a representation where relations are explicit (R), (b) a fixed list of geometric questions with exact answers (F), (c) layers that keep proposing and deciding apart (L), (d) a way to show the map to the model so it learns relations and not syntax (E), and (e) a way to measure and a safe order to grow (C).

A compiler is the closest analogy

3. The four premises: why map editing is hard

The document says a system that rejects any of these is outside its scope. Each premise creates a requirement.

P1. A map is a constrained artefact, not a document

A map is valid only if rules hold: roads join without gaps, every reference points to something that exists, lane numbers follow convention, values stay in range. An edit is correct only if the map stays valid. That makes editing constraint satisfaction dressed as text editing.

Requirement it creates: something that checks the rules after every edit (this becomes the authority, L5).

P2. Competence and authority are separable, and must be separated

“Can propose a good edit” and “can guarantee it is valid” are different abilities. Models have the first and not the second. A system that mixes them inherits the weaknesses of both. A system that separates them can improve the proposer forever without ever weakening the guarantee.

Requirement: two roles with a hard wall between them (L4 proposes, L5 decides).

P3. Competence here is relational, not lexical

Understanding a map means holding relations: what is beside what, what overlaps what along which axis, what continues into what. Remembering the XML tag names is not understanding. A model that only memorised the schema writes well-formed nonsense. A model that holds relations can propose something meaningful even in a format it has not seen.

Requirement: say exactly which relations count. That list is the F vocabulary (section 5).

P4. Storage formats are built for delivery, not editing

Formats store generating parameters instead of values, and carry meaning by position, with records implicitly valid “until the next one begins”. Three concrete OpenDRIVE consequences:

Why (b) matters concretely. Take a width cubic a=3.0, b=0.02, c=0.001 that starts at s = 0. Split it at s = 10 so a new record starts there. The correct new record is re-based: a′ = a + b·h + c·h² = 3.3, b′ = b + 2c·h = 0.04, c′ = 0.001 (h = 10). At 15 m into the new record the width is 4.125 m, the same as the original at s = 25. If you only copy the old record, you get 3.525 m, which is 0.6 m wrong. The old GREM pipeline made exactly this class of mistake: a lane width at s = 140 became 0 instead of 2.9553 after a lane-section split.

Requirement: keep the thing you reason and edit in separate from the thing you read and write. Formats become codecs at the edge. The middle is the IR (next section).

4. The internal map (layer L1) and its five requirements R1–R5

The document defines the internal map by requirements, not by a schema, so you can build it in any technology and check it against the list. Each requirement removes one P4 problem.

Req.It saysProblem it fixesConcrete example
R1 Stable identityEvery entity has an ID that survives renumbering, splitting, merging and round trips. Edits name entities; a structural path (“road 8, section 1, lane −3”) is only a derived view.Figure 4a: references break when a lane is inserted.The signal points at the lane’s permanent ID, not at “−3”. Resolved = sampled points in a local frame, authoritative for reasoning and for the model.Coefficients mean nothing; geometry predicates are awkward on formulas.The cubic is kept for export; the polyline is what “inside/beside/ahead” is computed on.
R4 Explicit extentsEvery value-carrying record states the interval it holds on.Figure 4b: implicit “until the next record”.Splitting is interval arithmetic: close one interval, open another, rebase the cubic.
R5 Provenance and confidenceEvery attribute records who asserted it, from what source, how certain.You cannot merge observed data with authored data, or prove a value did not come from the model.“s = 190.0, origin: computed by Q2 from road end − user’s 10 m”.

Why the IR must not be OpenDRIVE with a new name

The document warns: borrowing a format’s ontology (entity types, valid values, rules) is sound. Adopting its storage layout as the editing substrate brings P4 straight back. A representation validated against only one format absorbs that format’s assumptions without anyone noticing. The cheapest test of whether R1–R5 were met in substance is to add a second format with a different philosophy.

[my reading] Where OpenDRIVE leaks easily OpenDRIVE is road-centric: a spine plus lane widths measured from it. Lanelet2 and HERE are boundary-centric: lanes are strips between shared boundary lines, and “s” and “t” do not exist. If the IR stores “reference line + t offsets” as its core, it has already become OpenDRIVE. A safer core is boundaries as first-class entities with lanes referencing them; the OpenDRIVE door derives boundaries from the widths, and a Lanelet2 door reads them directly. The road ruler (s, t) can then be an optional, derived frame for formats that have one.

5. The five relation families F1–F5: what “understanding a map” means

The document says “geometric understanding” cannot be trained or tested until it is broken into a closed list of questions. Each family is one kind of question. Each has an exact evaluator in code and a notion of near-miss.

Three properties the vocabulary must have
  1. Completeness against the rules. Every normative rule of the standard should be expressible as a question from this list. A rule you cannot express is either a missing question or a genuine boundary, and the boundary must be declared with its reason. An undeclared gap is a false assurance.
  2. A graded distance D(r₁, r₂) per family. Saying “touches” where the truth is “overlaps” is a near-miss; saying “disjoint” is a category error. Without grading you have no loss signal, no useful benchmark and no basis for deciding whether a rejected proposal is worth retrying.
  3. Qualitative versus metric. F1–F4 are qualitative (a finite set of answers): a model can reason in them. F5 is metric (a number and a tolerance): no qualitative training produces it. So the model reasons in F1–F4 and requests F5; it never computes F5.

F1. Topology (the 2D footprint)

Predicates: equals, disjoint, touches, crosses, overlaps, contains, within. Governs containment and intersection of areas: is the placed object inside a traversable region? Evaluated with polygon operations on the resolved geometry.

Limit: it is 2D. A road on a bridge overlaps the road under it in plan view with no collision. [my reading] The project’s own review notes say vertical overlap is needed from the start.

F2. Interval (along the longitudinal axis)

Predicates (Allen’s interval relations): before, meets, overlaps, starts, during, finishes, equals, and their inverses. Governs the extent of every value-carrying record: lane segments, elevation and banking profiles, validity ranges. Pure interval arithmetic.

Why it needs R4: with explicit extents these are direct reads. With implicit “until next record”, each is an inference that you must redo and can get wrong.

F3. Order (across the lateral axis)

Predicates: left-of, right-of, immediately-adjacent, outward-from-centre, between, nth-from. Governs lane sequence, renumbering and ordinal reference (“the second lane from the edge”). It is a signed order on the lane index.

F4. Direction

Predicates: heading-aligned, opposing, facing, turns-left/right, on-the-left/right-side. Governs sign conventions, the orientation of directional furniture and manoeuvre direction. A cone calculus over heading and lateral sign.

F5. Continuity (the only metric family)

G0 position, G1 tangent, G2 curvature, each within a tolerance ε. Governs joins between geometric pieces, between roads and across profiles. Computed by endpoint evaluation and comparison.

Why one vocabulary, one implementation

The same F1–F5 code is used four ways. They are listed in the document as the reason the vocabulary is “the central artefact”:

UseWhat it does with F1–F5
Query interfaceThe model asks the engine: “is X inside Y?”, “which lanes lie between?”.
Admissibility rulesThe authority’s rules are written in F-terms: “no overlap with a drivable lane”, “G0 at this join”.
Training labelsRun the engine over many maps to label entity pairs automatically.
Evaluation scoresScore a proposal by graded distance D from the engine’s answer.

If each were implemented separately, they would drift apart silently and disagree exactly in the cases that matter. This is a correctness argument, not an efficiency argument.

6. The six layers L0–L5: who does what

L5 in detail: total, terminal, differential

  • Total and terminal: every change passes through it, nothing bypasses it, its verdict is final.
  • Deterministic.
  • It judges the map, not the proposal. It runs the rules on the state before and after, and only new problems count. A pre-existing defect is never blamed on the edit and never silently “repaired” alongside it. [This matters a lot: the real customer maps carry real defects.]

The three return paths (keep them distinct)

PathMeaningWhat happens
inadmissibleA proposal failed a check.The reason goes back to L4, which answers again under a bounded retry budget.
regressiveThe edit applied cleanly but left the map worse.Same return path, different reason, same budget.
under-determinedThe request cannot be resolved without information only the requester has.Nothing is attempted. A question goes to the user; the answer comes back as the next request against unchanged state. This is a success, not a failure, and should be measured as one. A system that never does it is guessing.

7. Encodings E1–E4: how to show the map to a model

L3 turns the IR into model input. The choices decide whether geometric competence is learnable at all. They are independent of which model you use.

RuleWhat it saysWhy
E1 Local frame, alwaysOrigin at the entity in question. Position along the road normalised by extent. Lateral offset kept in metres (widths carry meaning). Headings as (sin, cos) pairs. Curvature dimensionless.Translation, rotation and scale invariance for free: the same configuration looks the same wherever it occurs, so the model need not relearn it at every absolute coordinate. Sin/cos avoids the 359° vs 1° discontinuity.
E2 Typed graph, not serialised textEntities are nodes, F-relations are typed edges, geometry enters as resolved polyline features.Flattening to a document destroys the structure the vocabulary was defined to capture.
E3 Symbols as symbols, quantities as referencesCategories are symbols. A quantity in a proposal is a reference to a computed result, never a literal.A proposal that cannot express a literal cannot fabricate one. The hard rule becomes structural and holds regardless of model behaviour.
E4 Optional visual channelRendered top-down images through a vision encoder, fused later as a separate branch.Weak for exact values, strong for “this looks unusual”. Worth it mainly if you will also consume imagery.

The test of a good encoding: a model trained on it should transfer to a map it has never seen and to a format it has never been trained on, because the encoding exposes relations, not syntax.

8. Data, evaluation and the build levels (C0–C6)

Where training data comes from

L2 and L5 together are an automatic labeller. A deterministic evaluator over the vocabulary, plus a deterministic verdict on whether a map improved, is at once a labelling function, a reward function and a scorer.

RecipeConstructionCompetence taught
perturb → restoreCorrupt a valid map in a known way; the task is to repair it; the original is the target.Repair (and the “automated correction” use in section 9.1 of the document).
mask → recoverRemove an attribute and require it back.Attribute priors; the map is its own label.
compute → predictAsk a question the engine answers exactly.Quantitative intuition, unlimited volume.
enumerate relationsLabel entity pairs across all five families.The vocabulary itself.
round tripPropose, apply, emit, re-read, re-check.End-to-end edit validity.
threshold pairsThe same corruption at magnitudes straddling the tolerance.Where the decision boundary actually lies.

Two corpora are needed. Real maps give the true distribution but almost no negatives. Constructed data gives unlimited negatives, graded difficulty and exact truth, but a model trained only on it learns the generator’s assumptions. So: constructed data for curriculum and negatives, real data for distribution and held-out evaluation.

Six evaluation suites and two hard gates

SuiteItem → scoringWhat it protects
Relational(map, pair, family) → predicate, graded by DGeometric competence in isolation
Edit correctness(map, instruction) → expected change; exact on symbols, ε-tolerant on quantitiesThe core capability
Restorationcorrupted map → repaired mapCorrection workflows
Abstentionambiguous or impossible instructions → did it ask rather than guess?The highest-cost production failure
Non-regressionedits on maps with existing defects → no new defects, old ones untouchedThe L5 contract
Consequenceedits with known forced propagation → every required consequence applied and nothing beyondRepresentation and rewrite-rule correctness
Hard gates Two results are gates, not metrics to trade: non-regression and abstention accuracy. A gain elsewhere never compensates for a loss in either. Also: score accuracy-when-answering and abstention rate separately, split held-out data by whole map (not by edit), and treat cost (queries, tokens, latency) as a first-class metric.

The capability levels: build in this order

Two points to remember. First, C0 and C1 need no machine learning. The document argues much of the practical failure is the system being unable to express “immediately to the right of”, “between these two”, “nearest one facing this way”, not the model being unable to reason, so exposing the vocabulary as queries has the highest return per effort. Second, the decoupling rule: no level may make the system depend on a component that might not work. Every learned component sits behind a switch with the deterministic path as its fallback, and the system must run with all of them off.

9. Limits

The document’s own admissions

  • Tolerances. What ε means for each continuity grade is a domain decision, and it propagates into evaluation, admissibility and discrepancy detection.
  • Unexpressed rules. Rules the vocabulary cannot express must be listed with reasons, never dropped quietly.
  • Failure modes it lists: learned numbers leaking into the map; the representation work becoming the whole programme; constructed data being too easy; objectives satisfied degenerately (a no-op edit is admissible and non-regressive, so faithfulness must gate any reward); abstention decaying as the model gets stronger; the vocabulary silently under-covering; pre-existing defects blamed on edits; learned components becoming load-bearing.
  • Unknown: whether real before/after edit histories can be obtained; which model posture (small adapted model vs general model with critics) is better.
  • Conditions that should change the plan: if C1 and C3 close most of the gap, the higher levels may not be worth building (a success); if a second format needs special cases inside L1, the representation did not generalise; if abstention accuracy cannot be held, you have a suggestion engine, not an editor.

[my reading] Things the document does not settle

  • It says what the system must satisfy, not how to build it. Layer boundaries and the closed vocabulary are claims. Nobody has shown them sufficient yet; your C0 measurements are what would show it.
  • “C1 and C3 close most of the gap” is a hypothesis.
  • F1 on 2D footprints and F5 at joins go wrong if you compare the wrong things. Your own review notes recorded false alarms from comparing reference lines and t values at junction joins.
  • The cost is large: an IR with all five requirements, for every format, plus a relation engine and eval suites. That is why the document insists on levels.
  • The official ASAM checker (qc-opendrive) covers only a small share of the 1.9 rules, and a pole standing inside a driving lane passes it. So the placement rules in L5 are yours to write.

10. End to end: one request through everything

An invented tiny map, so every number can be followed.

User request: “Move signal 55 to 10 m before the junction.”
L0 + L1
Door in
The file is read through the OpenDRIVE door into the IR. The IR holds: signal:55 (permanent ID), road:8, its lanes, junction:J1, and edges attached_to(signal 55, road 8), successor(road 8, J1). Each value carries its origin (“imported from file, revision r1”). Unknown extras are stored raw. The file’s original bytes are archived.
L3
Model view
The model is shown a small local view, not the whole map: a graph (nodes: signal 55, road 8, lane −1, lane −2, J1; edges as above) with features in a local frame: signal 55 at 0.30 of the road’s length, t = −8.0 m, heading as (sin, cos). Categories like “signal” are symbols. No raw XML.
L4
Understand
model reads the request. It decides: operation = move; target = signal 55 (exists, unique); anchor = “the junction”. Question to itself: which junction? It asks L2: which junctions are connected to road 8? → only J1, at the end of the road. Unambiguous, so no question to the user. Distance = 10 m, given by the user, with unit metres (stated, not assumed). Nothing was said about t or orientation, so they stay as they are.
If it had been ambiguousIf road 8 had junctions at both ends, or the user said “move it near the junction”, the model returns the under-determined path with a question (“which end, and how far?”). Nothing is changed.
L2
Resolve
code answers the model’s queries exactly and hands back named handles: 
Q1 = end_of(road:8)                  → s = 200.0   origin: computed from road 8 geometry (length)
Q2 = Q1 − 10.0                        → s = 190.0   origin: computed; 10.0 from user
Q3 = lane_outer_edge(road:8, lane −2) → t = −7.0    (for later checks)
These are the F-queries in action: an interval/position question about the road’s end (F2 flavour), a lane-order question for the edge (F3).
L4
Plan
model proposes, using references, never literals (E3): 
{ "op": "move",
  "target": "signal:55",
  "set": { "s": { "ref": "Q2" } } }
code turns this into a change set: signal:55.s: 60.0 → 190.0, with the inverse for undo (190.0 → 60.0), a declared allowed scope (only signal:55.s), and a required effect (afterwards, s must equal 190.0 within tolerance). Model output stopped here; it has written no number.
L5
Verify
code applies the change to a copy and checks the difference between before and after:
CheckResult
Schema validpass
s inside the road: 0 ≤ 190 ≤ 200 (F2)pass
Footprint not inside a drivable lane (F1): t = −8.0 is beyond −7.0pass (disjoint)
No other object at (190, −8.0)pass
Orientation unchanged (F4)pass
Rule findings before vs after, compared by identity: the set of findings is the samepass (no new findings; old ones untouched)
Only allowed scope changed; required effect holdspass
L5 + L0
Apply
The candidate is exported through the door. Only the signal’s s attribute changes in the file; everything else, including content the system does not understand, keeps its bytes. The exported file is re-imported and compared to the candidate IR: only signal:55.s differs. The change is committed as revision r2. r1 stays available, so undo is simply another checked edit back to 60.0.
Respond
“Moved signal 55 on road 8 from s = 60.0 to s = 190.0, which is 10.0 m before junction J1. Nothing else changed.” Receipts (the checks that ran, with results) are attached.
