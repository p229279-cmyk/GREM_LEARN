Part A. Our pipeline (GREM-4): same idea, in time order

The document says who does what (layers). Our pipeline says when (stages). Same rule underneath: the model proposes, code decides every number.

UnderstandL3 L4 + L2 queriesDocument has one proposal layer. Ours stops earlier: it only decides what is asked and which things, and ends in propose / ask / refuse. “Refuse” (operation not supported) is ours.

Part B. The document’s own view (original)

1. The flow, with every letter placed

2. Follow one request through it

“Move signal 55 to 10 m before the junction.” Road 8 is 200 m long. Signal 55 is at s = 60.
#WhereWhat happens
1L0L1File becomes the IR. Signal 55, road 8 and junction J1 get permanent IDs (R1) and are linked (R2).
2L3Model is shown a small graph around signal 55, not the whole file.
3L4L2Model: “which junction touches road 8?” Engine: J1, at the end. So the request is clear.
4L2Engine computes Q1 = end of road 8 = 200.0 and Q2 = Q1 − 10 = 190.0. The 10 comes from the user. The model computed nothing.
5L4Model writes: set signal 55 s = Q2. A reference, not a number.
6L5L2Copy of the map gets the edit. Checks: s inside 0–200 (F2), signal not in a driving lane (F1), nothing else touched, no new rule problems.
7L5L0Commit. File written; only that one value changed. Re-read to prove it.

3. What goes wrong, and which arrow it takes

RequestResult
“Put it at s = 300” (road is 200 m)L5 rejects (F2) → back to the model → retry or ask.
“Put it in the right lane”Applies, but F1 says it sits in a driving lane. New problem → blocked.
“Add some signs to make it safer”Not answerable. Model asks the user. Map untouched.

4. Why each box exists

  • L0 + L1 + R: file formats store recipes and “valid until the next record”, so they are hard to edit. Edit a clean internal map instead.
  • L2 + F: “understanding a map” is a fixed list of questions. Code answers them exactly, so the model never guesses geometry.
  • L3 + E: show the model relations and references, not raw numbers, so it cannot invent a number.
  • L4 vs L5: proposing and deciding are different skills. The model proposes; code decides.
  • L5 compares before vs after: real maps already have defects. Only new ones are blamed on the edit.

Part C. From scratch, by hand: why each thing exists

Forget the pipeline. We start with nothing, do one job manually, and every time we get stuck we add exactly one thing. By the end, each letter is something we needed, not something we were told.

Step 1 · First try: give the file and the sentence to a language model

NeedThe new s value.

By handModel answers s="190". Correct here, because the road is straight and short.

WhyMake it real: a curved road, a 12 km map, “the middle of the road”. The model gives s="2" or 190.4: plausible, unmarked, wrong. (The old pipeline placed a “midpoint” sign 2 m in instead of 154 m, and said done.) Language is the model’s strength. Exact numbers are not.

So we addThe hard rule: the model never writes a number. So something else must produce the numbers. That something has to understand the map. Everything below is what that takes.

Step 2 · Do the job by hand: what questions must I answer?

NeedA list, in order.

By hand1) Which thing is “signal 55”? 2) Which road is it on? 3) Which junction is “the junction”? 4) Is it at the start or the end of road 8? 5) Where is that end, in s? 6) Subtract 10. 7) Is the new place a legal place for a signal? 8) Write it back without breaking anything else.

WhyLook at what kind of questions they are. 3–4 is “what is connected to what”. 5–6 is “where, along the road”. 7 is “is it inside a lane, which side, which way does it face”. These are the same few kinds of question every time.

So we addA fixed list of question types, answered by code: the relation families F1–F5. We did not choose them. The job forced them. Now each question gets its own step.

REASONING K1 · How do we know which questions to ask, in what order, and when to stop?

Correction first. I wrote “the job forced F1–F5”. That was too loose. The job forces some questions. The closed list is a design choice that has to be justified. Here is the mechanism.

The mechanism in 4 lines
1. Questions never come from the map. They come from two sources: the blanks the operation needs filled, and the rules that must hold afterwards.
2. Every question is one of a few kinds, decided by what you are asking about (along, across, area, facing, join, which-thing, connected-to).
3. They are asked in dependency order: you ask only when the inputs are known.
4. You stop when every blank has a value with an origin and every rule in scope passed. If a blank cannot be filled, you ask the user.

K1 relationships · the correction, drawn

The 8 questions I listed are examples from one job. Questions with the same meaning are grouped into a kind. The kinds are our design choice, justified in K1.2.

Our example, through it: “Move signal 55 to 10 m before the junction.” The form for move has two blanks: which thing and the new where. Which thing is filled by the user’s words plus a lookup (signal 55). Where splits into four: road by a link (road 8), along by the engine (end of road 8 − 10), across and facing by keeping the old values. If a blank cannot be filled, the process stops and asks the user.

K1.1 · Source A: the blanks (what the edit needs)

Each operation is a form with fixed blanks. A blank is filled by the user’s words, by a relation answer, or by asking. No blank, no question.

OperationBlanks it needs
querywhat to look for, which filter
addwhat kind · where · its attributes
movewhich thing · the new where
modifywhich thing · which attribute · new value
removewhich thing (and: what depends on it?)

And where is always the same four blanks. Any object on a road is located by exactly these:

BlankMeansFilled by
roadwhich roadlookup (R1), links (R2)
alonghow far along the roadF2 interval
acrosswhich lane / how far sidewaysF3 order
facingwhich way it pointsF4 direction

This is the real reason F2, F3, F4 exist: they are the coordinates of a thing on a road: (road, s, t, heading). Questions about area (F1) and joins (F5) belong to judging, not locating.

K1.2 · How questions are sorted: by what you are asking about

You are asking about…Words you will see in a sentenceKind

Why this list, and not another? Two checks, both from the document:

  • By what a map thing has: an identity, connections, a stretch along the road, a place across it, an area, a facing, and joins to its neighbours. Each is one kind of question.
  • By the rules: every rule of the standard should be expressible with these kinds. A rule that is not expressible must be listed as a declared gap.

The first two kinds are lookups in the IR (R1, R2). F1–F5 are the geometric ones.

K1.3 · Order: the dependency rule

  • Rule: ask a question only when everything it needs is already known.
  • You cannot compute Q2 = Q1 − 10 before Q1. You cannot find the end of “road 8” before you know which road. You cannot judge a place that does not exist yet.
  • So the order is not “F1 then F2…”. It is the order of what feeds what. For another sentence, the same four phases appear with other questions inside.

K1.4 · Source B: which rules are in scope (so we do not ask a million questions)

After the edit exists as a candidate, ask only the questions that the edit could have broken. Follow the links from what changed to what depends on it.

EditWhat it touchesQuestions in scopeNot in scope
move a signal along the roadone signal’s sF2 inside the road · F1 not in a driving lane · F4 facing still right for its side · no duplicate at the spotF5 (no geometry changed)
change a lane’s width from s=100width record, neighbours’ edgesF2 which records touched · F3 which lanes shift · F5 join to next section · F1 objects now overlapping a lanefacing of signals
delete a lanethe lane, things pointing at itR2 who pointed at it · F3 renumbering · F5 across sectionsnothing about signals’ s

Plus two checks every time: only what we said we would touch changed, and the result is what the user asked.

K1.5 · When to stop

  • Done when every blank has a value with an origin (said by user, or computed from X), and every rule in scope passed in the before-vs-after comparison.
  • Ask when a blank cannot be filled by words or by computation (missing, or two possible meanings).
  • Budget: a fixed number of tool calls and retries per request, then ask or refuse. (Your October plan uses 20 calls and 2 repairs.)

K1.6 · Test it on a different sentence and map

“Add a 50 km/h sign 20 m after the start of road 3, on the second lane from the edge, facing oncoming traffic.” Road 3 has lanes −1, −2, −3 on its right.

After the user answers (say: roadside, facing the traffic in lane −2), we reach the Judge phase. In scope for an add: new ID unique (R1) · s within the road (F2) · not inside any driving lane (F1) · no duplicate at that spot (F1) · facing consistent with the side (F4) · required attributes present. Not in scope: F5.

Same four phases, same kinds of question, different content. That is what makes it scale: a new map or sentence brings new combinations, not new kinds.

What is mine, what is the document’s. The document defines the closed vocabulary and the rule that every rule be expressible. It does not define this planning process. The blanks-and-rules process is my synthesis from that vocabulary, from GREM-3’s “Allowed / Required” idea and from your operation register. It is a proposal for you to challenge. Open: nobody has shown the list is complete. If a rule cannot be written with these kinds, we declare the gap instead of hiding it.

Step 3 · Names: “8” means two things

NeedPoint at things unambiguously.

By handIn the file, road 8 and junction 8 both have id “8”. “Remove 8” is ambiguous. Also: if I insert a new lane, lane −3 becomes lane −4, and anything saying “lane −3” now points at a different lane.

WhyNames in a file are labels that change or collide. If our own notes use them, they break the moment anything is edited.

So we addR1, permanent IDs. Give every thing its own internal name and remember the file label separately: road 8 → road:a1, junction 8 → junction:b7, signal 55 → signal:c3, lane −2 of road 8 → lane:d4. Renumbering changes the label, never the ID.

Step 4 · Reading the connections

NeedAnswer “which junction is at which end of road 8?”

By handRead <successor elementType="junction" elementId="8"/>. Successor means the end of the road. So junction 8 (now junction:b7) is at the end.

WhyBy hand I scan the XML each time. Slow, and I forget things: later, to delete a lane, I must find everything that points at it.

So we addR2, links as edges. Write it once as a line: road:a1 --successor--> junction:b7. “What touches road 8?” is now a lookup. “What points at this lane?” lists the things that would break.

Step 5 · Where is the end of the road, in numbers?

NeedQ1 = the s value of the end.

By handEasy answer: length="200". But is it true? The real geometry is a list of pieces (line, arc, spiral…), each with its own length. I should add them up: 200. On the real customer map, GREM-2 found 90 roads where the declared length and the pieces disagree.

WhyTrusting one attribute is exactly how the old pipeline went wrong. Also for “the middle of a curved road” you must evaluate the curve, and the curve parameter is not the distance (one old formula was off by up to 33 m).

So we addR3, shape stored twice. Keep the file’s formula (to write back exactly) and a computed version (points along the road) that code measures. Now Q1 = 200.0 is a measurement, not a guess.

Step 6 · Is the new place legal?

NeedIs (s=190, t=−8.0) inside a driving lane?

By handLane −1 is 3.5 wide, from t=0 to −3.5. Lane −2 is from −3.5 to −7.0. Signal at t=−8.0 is 1.0 m beyond the outer edge: outside, clear of traffic. If it had been t=−5, it would sit in lane −2: blocked. To get the widths I evaluated a + b·ds + c·ds² + d·ds³.

WhyWidths change along the road. A record says only where it starts; it “holds until the next record”. Width at s=137 with records (0: a=3.5) and (100: a=3.0, b=0.01)? Use the second, ds=37: 3.0+0.01·37 = 3.37 m. Insert a record and everything after quietly changes. If you split a record you must re-base it: copying a=3.0 b=0.02 c=0.001 to start at ds=10 gives 3.525 m at 15 m in; the true value is 4.125 m.

So we addR4, explicit extents. Every value states [start, end). Splitting is then closing one range and opening another. And the question “which records does s 140–160 touch?” is the interval family F2; “inside a lane?” is F1; “which lane is second from the edge?” is F3.

Step 7 · Units, and where did 190 come from?

NeedTrust the number, and be able to prove it.

By handUser says “10 m”. If they said “10 feet”: 10 ft = 3.048 m, so s = 200 − 3.048 = 196.952. (The old pipeline turned “150 ft” into s=2.0 instead of 45.72.) Then write down: s = 190.0, from: end of road 8 (200.0, measured) − 10 (said by user).

WhyWithout units, “50” is km/h or mph. Without the origin, nobody can tell a measured value from a default, and defaults sneaked in as if the user had said them.

So we addThe frame (units, axes) and R5, provenance: every value carries who said it and from what. “No value from the model” becomes checkable: no value has the origin “model”.

Step 8 · Don’t destroy what I don’t understand

NeedWrite the file back without losing anything.

By handSuppose signal 55 also holds a <userData> block I never read. If I rebuild the file from only what I understood, it vanishes. The old pipeline silently lost 104 elements and 422 attributes this way.

WhyAn edit that deletes data nobody asked about is a bug, even if the signal moved correctly.

So we addUnknown extras kept raw, and the original file archived (Revision). Exporting changes only the one value; everything else keeps its bytes.

Step 9 · So where is the model?

NeedTurn language into the right question.

By hand“Before the junction” → relation before, anchor = junction at the end of road 8, distance = 10 m. “Near the junction” → no distance → ask. “Past the junction” → different direction. If road 8 has junctions at both ends → ask which.

WhyThis is meaning, which a model does well. The model asks the engine (“what is at the end of road 8?”) and writes the answer as a reference, never a value.

So we addThe model writes set signal 55 s = Q2 where Q2 = Q1 − 10. Q1, Q2 come from code. This is E3: references, not literals. That is the whole job of the model here.

Step 10 · Judge the result, honestly

NeedDecide whether the edit is OK.

By handTake a copy, apply the edit, run the rules before and after. Say the map already has one defect: “0.3 m gap between road 8 and the next road”. Before: {gap}. After: {gap}. Same list → pass. If after shows {gap, signal inside lane} → the new item is ours → block.

WhyReal maps are already imperfect. “Zero problems required” would block every edit. “Count not higher” lets one problem swap for another. So compare which problems, not how many. Also check we only touched what we said (signal 55’s s) and that the result is what we asked (s = 190).

So we addA judge that compares before and after and decides; the model is not asked. And a way for it to say “back to the model, try again”, or “ask the user”.
