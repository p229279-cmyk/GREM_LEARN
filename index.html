The big picture on one page

A model decides what. Code decides every number and every verdict. Below: where each letter sits in the flow, and what happens to one request.

1. The flow, with every letter placed

2. Follow one request through it

“Move signal 55 to 10 m before the junction.” Road 8 is 200 m long. Signal 55 is at s = 60.
#WhereWhat happens
1L0L1File becomes the IR. Signal 55, road 8 and junction J1 get permanent IDs (R1) and are linked (R2).
2L3Model is shown a small graph around signal 55, not the whole file.
3L4L2Model: “which junction touches road 8?” Engine: J1, at the end. So the request is clear.
4L2Engine computes Q1 = end of road 8 = 200.0 and Q2 = Q1 − 10 = 190.0. The 10 comes from the user. The model computed nothing.
5L4Model writes: set signal 55 s = Q2. A reference, not a number.
6L5L2Copy of the map gets the edit. Checks: s inside 0–200 (F2), signal not in a driving lane (F1), nothing else touched, no new rule problems.
7L5L0Commit. File written; only that one value changed. Re-read to prove it.

3. What goes wrong, and which arrow it takes

RequestResult
“Put it at s = 300” (road is 200 m)L5 rejects (F2) → back to the model → retry or ask.
“Put it in the right lane”Applies, but F1 says it sits in a driving lane. New problem → blocked.
“Add some signs to make it safer”Not answerable. Model asks the user. Map untouched.

4. Why each box exists

  • L0 + L1 + R: file formats store recipes and “valid until the next record”, so they are hard to edit. Edit a clean internal map instead.
  • L2 + F: “understanding a map” is a fixed list of questions. Code answers them exactly, so the model never guesses geometry.
  • L3 + E: show the model relations and references, not raw numbers, so it cannot invent a number.
  • L4 vs L5: proposing and deciding are different skills. The model proposes; code decides.
  • L5 compares before vs after: real maps already have defects. Only new ones are blamed on the edit.
